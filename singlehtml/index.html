LAMMPS on HPC¶

A series of short tutorials for LAMMPS users who want to run molecular dynamics simulations on EuroHPC systems, with reference notes for GPU software compatibility.

Before you start¶

Prerequisites

  • Basic familiarity with Linux shell commands and molecular dynamics.

  • Access to an HPC system and an allocation for submitting jobs.

  • Familiarity with environment modules and Slurm job submission.

Short tutorials¶

Start with installation and compilation, then continue to the MACE workflow or inspect the prebuilt LAMMPS installations available through EESSI. The examples use specific software versions and cluster environments; adapt module names, paths, and allocation accounts to your system.

Episode 1: Installing LAMMPS on EuroHPC¶

Start by checking the LAMMPS installation on your HPC system. If it lacks the packages you need, compile your own CPU or GPU version. The build examples cover LUMI and Leonardo; the Slurm examples below cover LUMI.

Before you start¶

Prerequisites

  • An account on the target HPC system and an allocation for submitting jobs.

  • Basic familiarity with shell commands, environment modules, and Slurm.

  • Access to the compilers and libraries required by your chosen build.

1. Choose an installation¶

LAMMPS is the Large-scale Atomic/Molecular Massively Parallel Simulator. Its release types serve different needs:

Release type

Stable release

Check the LAMMPS release page when selecting a version. This tutorial uses 22 July 2025, update 3 as a specific example; it does not automatically select the newest release.

Load the module specified by your centre. A typical example is:

module load lammps
which lmp

which lmp should print the path to the executable. If it does not, check the module instructions and the executable name used by your installation.

Check enabled packages¶

LAMMPS uses a package system for features such as force fields and hardware acceleration. Check whether the installed executable includes the packages your simulation needs:

lmp -help | sed -n '/Installed packages:/,/List of individual/p'

Example output:

Installed packages:

GRAPHICS KOKKOS KSPACE MANYBODY MOLECULE RIGID

List of individual style options included in this LAMMPS executable

Your package list may differ. If a required package is missing, contact the centre’s support team or follow the compilation steps below. If the installed executable already meets your needs, you can skip those steps.

2. Prepare a source build¶

Use a separate working directory for this example. Run the following commands in one shell session so that LAMMPS_WORKDIR remains available:

mkdir -p lammps-eurohpc
cd lammps-eurohpc
export LAMMPS_WORKDIR="$PWD"
Check CMake¶

Load an appropriate CMake module if needed, then check the executable and version:

which cmake && cmake --version

The current LAMMPS CMake guide requires CMake 3.20 or later. Check the requirements of the source version you choose; the module examples in this tutorial use a newer CMake version.

Download and unpack the source¶

Run from LAMMPS_WORKDIR:

wget https://github.com/lammps/lammps/releases/download/stable_22Jul2025_update3/lammps-src-22Jul2025_update3.tar.gz

tar xf lammps-src-22Jul2025_update3.tar.gz

The extracted source directory contains the following files and subdirectories:

lammps-22Jul2025/
├── bench/
├── cmake/
├── doc/
├── examples/
├── fortran/
├── lib/
├── LICENSE
├── potentials/
├── python/
├── README
├── src/
├── third_party/
├── tools/
└── unittest/
Create directories and select packages¶

Run from LAMMPS_WORKDIR:

mkdir -p build lammps/22Jul2025/update3

The source, build, and installation directories are separate:

lammps-eurohpc/
├── lammps-22Jul2025/          # source
├── build/                    # CMake build and package preset
└── lammps/22Jul2025/update3/  # installation prefix

LAMMPS provides package presets under lammps-22Jul2025/cmake/presets/, including all_off.cmake, all_on.cmake, basic.cmake, and most.cmake. This example starts with most.cmake:

cp lammps-22Jul2025/cmake/presets/most.cmake build/pkgs.cmake

Edit build/pkgs.cmake to enable only the packages you need. Some packages have additional library requirements; selecting a smaller set can simplify the build.

3. Configure and compile LAMMPS¶

Choose one build recipe for your target system. Each recipe starts in LAMMPS_WORKDIR/build and installs to the same example prefix. Use separate build directories and installation prefixes if you want to keep multiple builds.

The GPU recipes enable KOKKOS. All recipes build a shared library, which is useful when linking LAMMPS to other software. Adapt the module names to those available on your system.

LUMI-C: CPU build¶
module purge
module load LUMI
module load partition/C
module load PrgEnv-cray
module load cray-fftw
module load cray-python

cd "$LAMMPS_WORKDIR/build"

prefix="$LAMMPS_WORKDIR/lammps/22Jul2025/update3"
cmake ../lammps-22Jul2025/cmake \
    -C ./pkgs.cmake \
    -DCMAKE_INSTALL_PREFIX="$prefix" \
    -DBUILD_SHARED_LIBS=yes \
    -DBUILD_MPI=yes \
    -DBUILD_OMP=yes \
    -DPKG_PYTHON=ON

make VERBOSE=1 -j 16 install

Check the installed executable¶

After the build completes, check that the executable can start in the loaded module environment:

"$LAMMPS_WORKDIR/lammps/22Jul2025/update3/bin/lmp" -help
cd "$LAMMPS_WORKDIR"

You should see LAMMPS help output and the enabled package list. If startup fails, check the build output, loaded modules, and shared-library search paths before submitting a job.

4. Run a LUMI test with Slurm¶

The following job scripts are for LUMI. If you compiled on Leonardo, use that system’s Slurm documentation to prepare a matching job script; Episode 2 includes a Leonardo Booster example for the MACE workflow.

Prepare the input¶

From LAMMPS_WORKDIR, copy the Lennard-Jones benchmark into an example directory:

cd "$LAMMPS_WORKDIR"
mkdir -p example
cp lammps-22Jul2025/bench/in.lj example/
cd example

Your working directory is now LAMMPS_WORKDIR/example. Save one of the following job scripts as job.sh in that directory. The relative installation path in each script assumes you submit the job from here.

LUMI-C: CPU job script¶
#!/bin/bash -l
#SBATCH --partition=debug # choose another queue for production
#SBATCH --nodes=1
#SBATCH --ntasks-per-node=128
#SBATCH --time=00:05:00 # increase for production runs

module purge
module load LUMI
module load partition/C
module load PrgEnv-cray
module load cray-fftw
module load cray-python

lmp_path=../lammps/22Jul2025/update3
export LD_LIBRARY_PATH="$lmp_path/lib64:$lmp_path/lib:${LD_LIBRARY_PATH:-}"
export OMP_NUM_THREADS=1

srun "$lmp_path/bin/lmp" -in in.lj -v x 3 -v y 3 -v z 3
LUMI-G: GPU job script¶
#!/bin/bash -l
#SBATCH --partition=dev-g # choose another queue for production
#SBATCH --nodes=1
#SBATCH --ntasks-per-node=8
#SBATCH --gpus-per-node=8
#SBATCH --time=00:05:00 # increase for production runs

module purge
module load LUMI
module load partition/G
module load PrgEnv-amd
module load cray-fftw
module load rocm
module load cray-python

lmp_path=../lammps/22Jul2025/update3
export LD_LIBRARY_PATH="$lmp_path/lib64:$lmp_path/lib:${LD_LIBRARY_PATH:-}"

export MPICH_GPU_SUPPORT_ENABLED=1
export OMP_NUM_THREADS=1
export OMP_PROC_BIND=spread
export OMP_PLACES=threads

srun "$lmp_path/bin/lmp" -in in.lj -k on g 8 -sf kk -pk kokkos -v x 8 -v y 8 -v z 8
Submit and inspect the job¶

Run from LAMMPS_WORKDIR/example. Replace xxxxxx with your allocation account:

sbatch -A xxxxxx job.sh

Slurm prints a job ID. When the job finishes, check its output and log.lammps for errors and the final simulation step.

Completion checklist¶

  • You can locate the LAMMPS executable and display its help output.

  • Its package list includes the features required by your simulation.

  • If you compiled LAMMPS, it is installed under the intended prefix.

  • Your test job starts the intended executable and finishes without errors.

Episode 2: LAMMPS with MACE on Leonardo Booster¶

This recipe builds LAMMPS with ML-IAP and MACE on Leonardo Booster, converts a model, and runs a copper simulation. We tested it on one A100 GPU on 13 October 2026 using the CUDA 12 stack below.

Before you start¶

Prerequisites

  • A Leonardo Booster account and a Slurm allocation with GPU access.

  • Familiarity with the installation workflow in Episode 1: Installing LAMMPS on EuroHPC.

  • Access to the compiler, MPI, CUDA, CMake, and Python modules listed below.

  • A working directory with enough space for the source trees, build, environment, Python wheels, and model file.

Tested configuration¶

Important

Start with the NVIDIA driver. Our Booster node had driver 535.274.02, which led us to choose a CUDA 12 toolkit and CUDA 12 Python packages. Under NVIDIA’s normal minor-version compatibility rules, CUDA 12.x requires driver branch 525 or newer, while CUDA 13.x requires branch 580 or newer.

Check nvidia-smi inside your GPU allocation before choosing software. See NVIDIA’s compatibility table.

Within CUDA 12, PyTorch 2.5.1+cu121 and cuEquivariance 0.4.0 passed our dependency and GPU checks. The other Python pins follow the MACE and build requirements; GCC, MPI, CMake, and Python come from Leonardo’s available modules. The LAMMPS and MACE release pins identify the sources we used.

We compiled LAMMPS with CUDA 12.2; the PyTorch wheel bundles a CUDA 12.1 runtime. That combination passed the tests below. See CUDA Driver, Toolkit, and Compute Capability Mapping (2026) for the driver, toolkit, and GPU architecture distinctions. If you change versions, repeat pip check and the GPU runtime check in step 5.

2. Prepare the Python environment and downloads¶

Load modules and create the environment¶

Run from LAMMPS_MACE_WORKDIR:

module purge
module load cmake/3.27.9
module load gcc/12.2.0
module load cuda/12.2
module load openmpi/4.1.6--gcc--12.2.0-cuda-12.2
module load fftw/3.3.10--openmpi--4.1.6--gcc--12.2.0-spack0.22
module load python/3.11.7

export PYTHONNOUSERSITE=1
python -m venv lammps_mace_venv
source lammps_mace_venv/bin/activate
python -m pip install --upgrade pip

Check python --version and python -m pip --version: Python should report 3.11, and pip should point into lammps_mace_venv. Use this same environment when building LAMMPS and running its Python interface.

Resolve the runtime packages before compiling¶

Save the following as constraints.txt in the project root:

numpy==1.26.4
e3nn==0.4.4
torch==2.5.1+cu121
cuequivariance==0.4.0
cuequivariance-torch==0.4.0
cuequivariance-ops-torch-cu12==0.4.0
cupy-cuda12x==13.3.0
Cython==3.0.12

Ask pip to resolve MACE and the GPU packages together. First inspect the dry-run report, then install using the same constraints:

cd "$LAMMPS_MACE_WORKDIR"
python -m pip install --dry-run --report resolver-report.json \
  -c constraints.txt --extra-index-url https://download.pytorch.org/whl/cu121 \
  ./mace torch cuequivariance cuequivariance-torch \
  cuequivariance-ops-torch-cu12 cupy-cuda12x Cython

python -m pip install --report installed-report.json \
  -c constraints.txt --extra-index-url https://download.pytorch.org/whl/cu121 \
  ./mace torch cuequivariance cuequivariance-torch \
  cuequivariance-ops-torch-cu12 cupy-cuda12x Cython

python -m pip check
python -m pip freeze --all > requirements-resolved.txt

Continue only if pip check reports no conflicts. The constraints select the main components; requirements-resolved.txt records the full environment, including dependencies selected by pip. Keep it with the build records. Do not change NumPy or Cython after configuring the Python-enabled build.

Note

cuEquivariance 0.8.1 required a newer cuBLAS dependency than the one pinned by PyTorch 2.5.1+cu121 in our installation attempt. Version 0.4.0 passed the runtime and numerical tests below. Using --no-deps would bypass the dependency check; it does not resolve that conflict.

Prepare downloads for the compute node¶

The allocated compute nodes used in this test could not download from PyPI. LAMMPS’s install-python target creates a temporary environment to build its Python wheel, so download its build requirements now:

mkdir -p wheelhouse models test
python -m pip download --only-binary=:all: --dest wheelhouse \
  -r lammps/python/wheel_requirements.txt

wget -O models/mace-mp-0b3-medium.model \
  https://huggingface.co/mace-foundations/mace-mp-0/resolve/main/mace-mp-0b3-medium.model

printf '%s  %s\n' \
  '2f2be696351ac9e94fbe01cdfb6f017679acdbd2db7645209ef55fec9826b012' \
  'models/mace-mp-0b3-medium.model' | sha256sum --check

The checksum should report OK. Convert the model later, inside a GPU allocation.

3. Save a shared build and runtime environment¶

Save the following as environment.sh in the project root. Both Slurm jobs will source this file, so their modules, Python interpreter, and library paths stay consistent:

export LAMMPS_MACE_WORKDIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"

module purge
module load cmake/3.27.9
module load gcc/12.2.0
module load cuda/12.2
module load openmpi/4.1.6--gcc--12.2.0-cuda-12.2
module load fftw/3.3.10--openmpi--4.1.6--gcc--12.2.0-spack0.22
module load python/3.11.7

export PYTHONNOUSERSITE=1
source "$LAMMPS_MACE_WORKDIR/lammps_mace_venv/bin/activate"
export NVCC_WRAPPER_DEFAULT_COMPILER="$(command -v g++)"
export PATH="$LAMMPS_MACE_WORKDIR/lammps-mace/bin:$PATH"

LMP_CXX_RUNTIME="$(g++ -print-file-name=libstdc++.so.6)"
export LD_LIBRARY_PATH="$(dirname "$LMP_CXX_RUNTIME"):$LAMMPS_MACE_WORKDIR/lammps-mace/lib64:$LAMMPS_MACE_WORKDIR/lammps-mace/lib:${LD_LIBRARY_PATH:-}"
export LD_PRELOAD="$LMP_CXX_RUNTIME${LD_PRELOAD:+:$LD_PRELOAD}"

export OMP_NUM_THREADS=1
export XDG_CACHE_HOME="$LAMMPS_MACE_WORKDIR/cache"
export TORCH_HOME="$XDG_CACHE_HOME/torch"
export TORCH_EXTENSIONS_DIR="$XDG_CACHE_HOME/torch_extensions"
export CUPY_CACHE_DIR="$XDG_CACHE_HOME/cupy"
export CUDA_CACHE_PATH="$XDG_CACHE_HOME/cuda"

The GCC runtime selection is needed for this Leonardo module combination. During testing, Python loaded an older libstdc++ and importing LAMMPS failed with a missing GLIBCXX_3.4.29 symbol. Adding the GCC 12 library directory to LD_LIBRARY_PATH alone did not fix it; preloading the library selected by g++ did. Reassess this workaround if the centre changes its modules.

4. Compile LAMMPS in an allocation¶

The build enables only the packages needed by this recipe:

Option

Purpose

kokkos-cuda.cmake preset

Enable KOKKOS/CUDA and select nvcc_wrapper.

BUILD_MPI, BUILD_OMP

MPI and OpenMP support.

BUILD_SHARED_LIBS

A shared LAMMPS library for the Python interface.

PKG_PYTHON

Python support.

PKG_ML-IAP, MLIAP_ENABLE_PYTHON

The Python-enabled ML-IAP interface.

PKG_ML-SNAP

A supporting package enabled in the tested build.

Kokkos_ARCH_AMPERE80, Kokkos_ARCH_ICX

GPU and host architecture settings used on Booster.

Save the following as build.sbatch in the project root. Replace the allocation placeholder with your account. The debug allocation keeps compilation off the login node and provides the same environment used for the GPU test.

--qos=boost_qos_dbg selects Booster’s debug Quality of Service (QoS) within the boost_usr_prod partition. It is intended for short tests and has a maximum walltime of 30 minutes. For production runs, remove or replace this directive with a QoS appropriate to your allocation and adjust the time limit. Check the Leonardo scheduling limits before submitting.

#!/bin/bash
#SBATCH --job-name=lammps-mace-build
#SBATCH --partition=boost_usr_prod
# Debug QoS for short tests; maximum walltime 30 minutes.
#SBATCH --qos=boost_qos_dbg
#SBATCH --account=EUHPC_XXX_XXX
#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=8
#SBATCH --gres=gpu:1
#SBATCH --mem=32G
#SBATCH --time=00:30:00

set -euo pipefail
cd "$SLURM_SUBMIT_DIR"
source ./environment.sh

export PIP_CONFIG_FILE=/dev/null
export PIP_NO_INDEX=1
export PIP_FIND_LINKS="$LAMMPS_MACE_WORKDIR/wheelhouse"
export PIP_DISABLE_PIP_VERSION_CHECK=1
export PIP_CACHE_DIR="$LAMMPS_MACE_WORKDIR/cache/pip"

cmake -S lammps/cmake -B build \
  -C lammps/cmake/presets/kokkos-cuda.cmake \
  -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_CXX_USE_RESPONSE_FILE_FOR_OBJECTS=OFF \
  -DCMAKE_INSTALL_PREFIX="$LAMMPS_MACE_WORKDIR/lammps-mace" \
  -DPython_EXECUTABLE="$LAMMPS_MACE_WORKDIR/lammps_mace_venv/bin/python" \
  -DBUILD_MPI=ON -DBUILD_SHARED_LIBS=ON -DBUILD_OMP=ON \
  -DPKG_PYTHON=ON -DPKG_ML-IAP=ON -DMLIAP_ENABLE_PYTHON=ON \
  -DPKG_ML-SNAP=ON \
  -DKokkos_ARCH_AMPERE80=ON -DKokkos_ARCH_ICX=ON \
  -DKokkos_ENABLE_OPENMP=ON \
  -DMPI_CXX_COMPILER="$(command -v mpicxx)"

cmake --build build --parallel "$SLURM_CPUS_PER_TASK"
cmake --install build
cmake --build build --target install-python
python -m pip check
python -m pip freeze --all > requirements-final.txt

The CUDA preset selects the compiler wrapper; leave CMAKE_CXX_COMPILER unset. The response-file option avoids a linking failure encountered with nvcc_wrapper on this toolchain. Additional packages such as KSPACE or MOLECULE can be enabled later if your input needs them.

Submit from the project root:

cd "$LAMMPS_MACE_WORKDIR"
sbatch build.sbatch

Wait for successful completion before submitting the simulation job. Check the Slurm output for the intended Python interpreter, CUDA toolkit, and MPI implementation, and confirm that lammps-mace/bin/lmp was installed. If compilation exceeds the debug time limit, request a suitable allocation; rerunning the same script reuses completed build objects.

5. Verify the runtime environment¶

Save the following as check_runtime.py in the project root. The simulation job in the next step runs it on the allocated GPU before converting the model:

from importlib import metadata

import cupy as cp

1. Understand the EESSI selection¶

EESSI is the European Environment for Scientific Software Installations. It provides software builds for different CPU and accelerator architectures and forms the basis of the EuroHPC Federation Platform’s Federated Software Catalog.

EESSI selects compatible builds by detecting the hardware on the node where you initialize it. The EuroHPC system name does not select the software. Site configuration determines how the repository is mounted and how host libraries, such as the NVIDIA driver, are exposed.

Keep three choices separate:

Choice

What it controls

Access method

How the EESSI repository becomes available.

EESSI release

Which software collection you inspect.

CPU and accelerator targets

Which compatible builds are visible.

An EESSI release name such as 2025.06 is not a LAMMPS version. Read the full module name and check the executable before choosing an installation.

Create a working directory within your project scratch space:

2. Access EESSI on Leonardo Booster¶

Check the system-specific instructions¶

The EFP Leonardo instructions describe compute-node access using a Slurm job name containing _CVMFS_, followed by EESSI initialization. They also retain a warning about non-interactive and multi-node usage.

In our tests, the job-name trigger alone did not mount EESSI in either a batch job or an interactive Booster allocation. The site-provided eessi/1.0 launcher did mount the repository successfully on allocated compute nodes. The recipe below uses the site launcher.

Record the available modules¶

Save the following as inventory.sbatch in the project root. Replace the account placeholder with your allocation account and submit from this directory:

--qos=boost_qos_dbg selects Leonardo Booster’s debug Quality of Service (QoS) for short tests within the boost_usr_prod partition. It has a maximum walltime of 30 minutes and higher scheduling priority than the normal QoS; allocation time still depends on resource availability. For production runs, remove or replace this directive with a QoS appropriate to your allocation and adjust the time limit. Check the current Leonardo scheduling limits.

#!/bin/bash
#SBATCH --job-name=eessi-lammps-inventory
#SBATCH --partition=boost_usr_prod
# Debug QoS for short tests; maximum walltime 30 minutes.
#SBATCH --qos=boost_qos_dbg
#SBATCH --account=EUHPC_XXX_XXX
#SBATCH --nodes=1
#SBATCH --ntasks=1
#SBATCH --cpus-per-task=2
#SBATCH --gres=gpu:1
#SBATCH --mem=8G
#SBATCH --time=00:10:00

module load eessi/1.0

  module --force purge
  if ! module load "EESSI/$version"; then
    printf 'EESSI %s is unavailable\n' "$version"
    continue
  fi

4. Prepare the official EESSI container¶

Run these downloads on a login node. The compute-node checks will reuse the local image rather than pulling it during an allocation.

Download the launcher and image¶
cd "$EESSI_LAMMPS_WORKDIR"
git clone https://github.com/EESSI/software-layer-scripts.git
git -C software-layer-scripts checkout 6327b3a782f4a17ec54cc2f809624980e33a2f64

module load profile/global
module load singularityce/4.3.3
singularity --version

mkdir -p images cache tmp
export SINGULARITY_CACHEDIR="$PWD/cache"
export SINGULARITY_TMPDIR="$PWD/tmp"
singularity pull images/eessi-debian12.sif \
  docker://ghcr.io/eessi/build-node:debian12

sha256sum images/eessi-debian12.sif > images/eessi-debian12.sif.sha256

The image is published by EESSI. The debian12 tag can change, so keep the launcher revision and the checksum of your downloaded SIF with your records. Initial download and conversion can take several minutes.

Choose the repository access method¶

The official launcher can mount EESSI inside the container using FUSE. In our independent-mount test, the container started and accessed the GPU, but CVMFS failed to initialize the root catalogue. That test could not list EESSI modules.

The working recipe instead binds the repository mounted by Leonardo’s site launcher into the container. It therefore still needs a working host EESSI mount. The launcher uses --repository None to disable its repository mounting, then receives an explicit read-only bind for the existing repository.

Singularity also reported a squashfuse permission failure in our tests and fell back to extracting the SIF. That fallback allowed the container to run; it was separate from the failed CVMFS catalogue fetch.

5. Inspect EESSI inside the container¶

Save the inspection script¶

Save the following as inspect-container.sh in the project root. The job binds that directory to /work inside the container:

#!/bin/bash
set -eo pipefail
cd /work
ls /cvmfs/software.eessi.io/versions
nvidia-smi --query-gpu=name,driver_version --format=csv,noheader

/usr/bin/python3 - <<'PY'
import ctypes

cuda = ctypes.CDLL("libcuda.so.1")
assert cuda.cuInit(0) == 0, "CUDA driver initialization failed"
count = ctypes.c_int()
assert cuda.cuDeviceGetCount(ctypes.byref(count)) == 0
assert count.value == 1, "This example expects one visible GPU"
print("CUDA driver check passed; visible GPUs:", count.value)
PY

source /cvmfs/software.eessi.io/versions/2025.06/init/lmod/bash

for version in 2023.06 2025.06 2026.06; do
  module --force purge
  export EESSI_ACCELERATOR_TARGET_OVERRIDE=accel/nvidia/cc80
  if ! module load "EESSI/$version"; then
    printf 'EESSI %s is unavailable\n' "$version"
    continue
  fi
  module -t avail 2>&1 | grep -E '^LAMMPS/[0-9]' | sort -u \
    > "container-lammps-modules-$version.txt" || true
  cat "container-lammps-modules-$version.txt"
done

module --force purge
export EESSI_ACCELERATOR_TARGET_OVERRIDE=accel/nvidia/cc80
module load EESSI/2023.06
module load LAMMPS/2Aug2023_update2-foss-2023a-kokkos-CUDA-12.1.1

timeout 45 mpirun --mca pml ob1 --mca btl self,tcp -np 1 lmp -h \
  > container-lammps-help.txt 2>&1

grep -a 'KOKKOS package API' container-lammps-help.txt
sed -n '/Installed packages:/,/List of individual/p' container-lammps-help.txt
python -c 'import lammps.mliap; print("ML-IAP Python import passed")'

The container detected Ice Lake automatically, but EESSI did not automatically identify the accelerator there. The explicit cc80 override matches the A100 verified by nvidia-smi and the CUDA driver check. It selects the GPU module collection for that hardware.

We used this mpirun command only for a one-process help check. For simulations, use a centre-supported MPI setup and test it at the node count you plan to use.

Save the container job¶

Save the following as container.sbatch in the project root. Replace the account placeholder before submitting:

#!/bin/bash
#SBATCH --job-name=eessi-lammps-container
#SBATCH --partition=boost_usr_prod
# Debug QoS for short tests; maximum walltime 30 minutes.

  --container "$PWD/images/eessi-debian12.sif" \

  --extra-bind-paths "$PWD:/work,/cvmfs/software.eessi.io:/cvmfs/software.eessi.io:ro" \

Loading the site EESSI environment changes the host module environment.
